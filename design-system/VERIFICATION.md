## 3. Other QA findings

### 3a. Notifications "Mark all as read" (recorded for a future phase, not fixed)
Prototype: `<button class="text-[13px] font-bold hover:underline shrink-0 cursor-pointer">` -> 19.5 px high, no padding. Next.js: `shrink-0 pb-1 text-[13px] font-bold text-primary hover:underline disabled:cursor-not-allowed disabled:opacity-60 disabled:no-underline` -> 23.5 px high (4 px bottom padding), plus a disabled state the prototype lacks. Cause: the extra `pb-1` (`features/notifications/components/notifications-page.tsx`). Class V (plus a harmless disabled style). Fix: drop `pb-1`.

### 3b. The "probe artefacts" on Submit and the Chair pages: **corrected conclusion**
I previously called them probe-pairing artefacts. Inspection of the real DOM (`qa/inspect-pairs.mjs`) shows that was wrong, or at best misleading:
- For every flagged label there is exactly **one element on each side with identical text, and the Next.js label points at the same kind of control**; the pairing is correct.
- They are **not regressions**: the baseline held the same property diffs under keys with the asterisk (`label|title *`); my "new diffs" script compared key strings, so a renamed key looked new.
- They are **real, pre-existing visual mismatches** of the shared `Field` label (`text-xs font-bold text-ink-soft mb-1`, 12 px / 700):

| Page | Prototype label | Next.js label |
|---|---|---|
| Submit (New Submission) "Title" | 14 px / 600, `mb-1.5`, colour `--text`, width 614 | 12 px / 700, `mb-1`, ink-soft, width 694 |
| Peer Review > Manage "Review of the submission" | 14 px / 600, inline (`flex items-center gap-2`, width ~179), mb 0, colour `--text` | 12 px / 700, block, mb 4, ink-soft |
| Conference Details "Website", "Conference title", "Primary area" | 12 px / **600**, `mb-1.5`, `--text-soft` (with a help "?" popover) | 12 px / **700**, `mb-1`, ink-soft |
| Review settings "From" | 12 px / 600, `mb-1.5`, `--text-muted`, **red `*` marker** | 12 px / 700, `mb-1`, ink-soft, **no `*`** (a required-marker difference) |
| Manage Submissions "Title", "Abstract" | 14 px / 600, `mb-1.5` | **identical** (that page does not use `Field`) |

So the prototype itself uses **several label styles** (14/600, 12/600 and others, per page), and the shared Next.js `Field` fits none of them except by chance. A fix must follow each page's prototype style, not one global change. Also flagged earlier on mobile (390 px): Next.js content is 308 px wide where the prototype's is 276 px (a container padding difference, unrelated to labels).
- Two real probe weaknesses found: (1) the style key strips the required `*`, so a missing or extra asterisk is invisible to style pairing (the field-level `required` check still catches it for inputs, but not for plain labels like "From"); (2) my regression script keyed diffs by name. Both are fixable in `qa/probe.mjs` (compare the asterisk as its own property; key regression sets by element order).
- The header "Conferences" width (125.8 vs 129.1 px): the odd 125.8 value came from the **prototype** side. 24 further loads (prototype, Next.js, Next.js dashboard) all measured 129.11 px. Consistent with the prototype loading its web font through a remote CSS `@import` (a late font swap), but **not reproduced**, so "likely, not proven". The harness should serve one local copy of the font to both apps to remove the variable.

### 3c. Profile, Settings, Complete profile: what is needed to test them safely
Why blocked: the Next.js profile screens read the signed-in Supabase user (`getProfileService` -> `profiles`, `profile_details`, storage bucket `public`); the proxy gate checks a session cookie with `getClaims()`; `UserMenu` / `ProfileProgress` render only with a ready profile; mock mode has no accounts (by design).
Safe plan (no real Supabase, no real account):
1. A small local **fake Supabase** (a Node HTTP server in `qa/`, bound to 127.0.0.1) answering only: `GET /auth/v1/user` (and `POST /auth/v1/token` for refresh), `GET/PATCH/POST /rest/v1/profiles` and `/profile_details`, and storage upload for the photo bucket. Point a QA-only Next instance at it with `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:<port>` and a dummy anon key (as done for the auth-pages instance). No `.env*` file is touched. (PORT-PLAN mentions an earlier `fakesb.mjs`; it is not in the repository.)
2. A **session cookie injected by Playwright** (`sb-<host>-auth-token`) carrying a JWT-shaped dummy token: the fake accepts any bearer, so no login flow runs.
3. **One synthetic person used on both sides**: the prototype reads its profile from `localStorage["grs_profile"]` (see `shared/auth.js`), so the same synthetic JSON is loaded there and returned by the fake rows. This avoids copying the prototype's built-in sample profile (it contains what looks like personal contact details).
4. **Hard safety guards** in the harness: abort every request whose host is not localhost, log all requests, fail the run if any host except 127.0.0.1 / the two app ports was contacted.
5. States to cover: complete profile (green pill, avatar), incomplete profile (progress pill), the "complete your profile" gate with missing required fields, and Settings tabs; photo upload and phone / institution pickers against the fake.
Effort: roughly a day for the fake and the profile fixtures; it would also unlock the header avatar / pill, `PhoneField`, `PhotoField`, `ProfileAvatar`, institution pickers and `PasswordField` in Settings (all modified in the last phase and still untested).

## 4. Mock-mode versus production, and disclosures
- Everything measured is **mock / sample mode**: Next.js on mock fixtures (or an enabled form against an unreachable dummy Supabase URL) versus the prototype on sample data. No real sign-in, registration or submission was run; no real Supabase was contacted; no `.env*` file changed.
- **Maps key usage:** the prototype's configured Google Maps key was used for **three map loads** in this phase (In-Person and Hybrid in `evidence.mjs`, one in `evidence2.mjs`). No Places queries were typed. The key value was never read or printed.
- The prototype's Smart Fill was deliberately **not** triggered (it would call the AI service).
- Items needing a real (production) check later: the header pill and avatar, the Register photo save after sign-up, the `Create Conference` button text for real accounts, and the prototype in database mode.
