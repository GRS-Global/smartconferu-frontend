# Smartconferu — Next.js frontend

Production frontend being ported screen by screen from the Vite prototype (`../src`, served at `/prototype`). The prototype stays untouched and runnable (`npm run dev` in the repo root). This folder is its own git repository; the prototype repo ignores it.

## Commands

```bash
cd frontend
npm install
cp .env.example .env.local   # fill in the two Supabase values (same project as the prototype's VITE_ ones)
npm run dev                  # http://localhost:3000  (redirects to /dashboard)
npm run typecheck            # next typegen + tsc --noEmit
npm run lint
npm run build
```

## Data

`NEXT_PUBLIC_DATA_SOURCE`: `supabase` (default) or `mock` (typed fixtures in `src/mocks`, UI work only). **There is no fallback between them**: without Supabase keys the dashboard shows a configuration error, without a session it asks you to sign in, a failed request shows an error with "Try again", and an account with nothing shows an empty state.

`src/services/supabase/conferences.ts` reads the signed-in user's conferences straight from Supabase with the anon key and their session, like the prototype's `loadWorkspace()`. It invents nothing: tables, columns, RLS and RPCs are the ones in `../supabase/migrations` (`conferences`, `conference_members`, `submissions`, `submission_authors`, `review_assignments`, `reviews`, RPC `respond_to_invitation`, `claim_my_papers`). Not in the database yet, so empty here: certificates, committee roles, reviewer achievements, registrations as a separate record (a registered paper is `outcome = 'registered'`).

## Authentication and sessions

- `/login`: email + password, "Email me a login code" (one-time code), "Forgot password?" and the SSO buttons (which say "coming soon", as in the prototype's database mode). "Register here" opens `/register`.
- `/register` ("Create Account", the prototype's RegisterPage): first / last name, email, affiliation (institution picker, same as My Profile) and department, designation, country, gender, website, mobile number with notification channels, password + retype (show / hide), and the Terms of Service tick (ticked to start with, as in the prototype; Continue stays disabled without it). The rules and messages are the prototype's (and Complete Profile's), shown live once a field has been left; "Show me" brings the first problem into view. The account is made with Supabase Auth `signUp`; the details that aren't sign-in data wait in the sign-up metadata with `signup_pending: true` until the first session exists, then `applySignupDetails` copies them onto the profile (see below). With "Confirm email" on, a "Check your email" screen follows (Resend confirmation email, "Used the wrong email?"); with it off the person is signed in at once and goes to My Conferences. An address that is already registered says so (Supabase answers with a user that has no identities when "Confirm email" is on). **Not ported:** the photo step (a photo can only be stored once there is a session, and with "Confirm email" on there isn't one; add it in My Profile) and the prototype's preview of the emails that will be sent.
- `/reset-password` (the prototype's ResetPasswordPage): where the emailed link lands. The form appears only when the link produced a recovery session (`PASSWORD_RECOVERY`); no link, an expired / used link, a link made by the prototype, or a link opened in another browser each show a sentence and "Back to sign in". New password: at least 6 characters, retyped, then `updateUser({ password })`; "Password updated" only after Auth accepts it (its own rules, e.g. "must differ from the current one", are shown in plain words), then the person is signed in and sent to My Conferences. Passwords go only to the Auth API: never into a URL, a log or storage.
- **Email links are PKCE links, not the prototype's.** This app's Supabase client (`@supabase/ssr`) uses the PKCE flow: the sign-up confirmation, one-time-code and reset links come back as `?code=…` and the client exchanges the code on load using a verifier it stored in this browser when the email was requested. So a link only works in the browser that asked for it (opened elsewhere, a sign-up confirmation still confirms the address, so the person can simply sign in; a reset link has to be requested again). Links made by the prototype use the older implicit flow (`#access_token=…`); this client rejects them ("Not a valid PKCE flow url"), so `/reset-password` says so instead of failing silently. No callback route is needed: the client exchanges the code itself. Reading what the link left in the address bar is done once per page load (`features/auth/email-link.ts`) because the client cleans the address bar.
- **Supabase settings these screens depend on** (Dashboard → Authentication; documented here, not changed by this app): **URL Configuration** must list this app's address in *Redirect URLs*: `<origin>/login` (sign-up confirmation, login-code link) and `<origin>/reset-password`, for every origin that serves the app (e.g. `http://localhost:3000` in development, the production domain), or Supabase falls back to the Site URL; **Providers → Email → Confirm email** decides which of the two sign-up outcomes happens (both are handled); the email templates in `../supabase/email-templates` must keep `{{ .ConfirmationURL }}` (the PKCE link); and the built-in mailer's send limits apply while testing ("Too many emails…" / "Please wait N seconds" are shown in plain words).
- Session: `@supabase/ssr` keeps it in cookies (no tokens in localStorage). `src/proxy.ts` refreshes the session and does optimistic redirects: signed out → `/login?next=…`, signed in on `/login` or `/register` → where they were going. `/register` and `/reset-password` are open to signed-out visitors; `/reset-password` stays open to signed-in ones because the emailed link signs the person in before the new password is set. It only verifies the signed JWT (`getClaims`); data access is enforced by Row Level Security. `?next=` is accepted only as a path inside this app (never the sign-in, register or reset pages).
- Session end (expired token, sign-out in another tab) sends the user back to `/login?reason=expired`; the dashboard clears the local session first, so there is no redirect loop.
- Mock mode (`NEXT_PUBLIC_DATA_SOURCE=mock`) has no accounts: nothing is gated, no Supabase request is ever made, `/login`, `/register` and `/reset-password` say so. Without the Supabase keys the same three pages say that instead.
- Sign-up details are applied **exactly once**: loads that overlap (React Strict Mode, a quick reload) share one run per account; `signup_pending` is cleared only after the profile rows were written, and a failure to clear it is reported rather than ignored; and a retry (flag still set after a partial failure) only fills what is still empty, so it can never undo what the person edited in the meantime.
- Still in the prototype: SSO sign-in (the buttons say "coming soon").

## Profile and completeness

- Data: the same rows the prototype uses. `profiles` (first_name, last_name, designation, affiliation, country, orcid_id, photo_path: the only columns the browser may write, per the column grants in `0001_core_schema.sql`) and one JSON blob in `profile_details.data` (owner-only). Saves merge into the stored blob, so data this app doesn't edit (experience, education, memberships…) is preserved. The photo goes to the public `public` bucket under the user's own folder.
- Completeness (`features/profile/completeness.ts`) is a port of the prototype's `getProfileCompleteness`: required = first name, last name, email, affiliation, designation, country, gender; the score weights the General / Scholar / Professional / Contact tabs.
- Gate (`ProfileGate`, in the signed-in layout): profile loading → placeholder; profile **failed to load** → "Couldn't load your profile" + Try again (never read as incomplete); loaded but missing required details → `/complete-profile?next=<page>`; complete → the page. `/complete-profile` sends complete accounts straight on to `next` (a safe in-app path), so the two never loop.
- `applySignupDetails` (in `services/supabase/profile.ts`): runs when the profile is loaded and the account's `signup_pending` metadata flag is set (registration in the prototype sets it): copies affiliation/designation/country onto `profiles` and the detail keys into `profile_details`, then clears the flag. Failures are logged and retried at the next load.
- My Profile (`/profile`): the prototype's showcase page: header card (photo, name, designation, institution, member since, featured society chips: joined / ended / greyed "add", "Find me on" icons), sticky About / Affiliation / Experience / Education / Memberships tabs, and a private Contact details sidebar. Every card's pencil (and the round + on Experience / Education / Memberships) opens its editor in a dialog, ported from the prototype: intro (name, designation, gender, country, website, city, state), photo (crop with drag / zoom / rotate / keyboard, remove, default avatar), about (bio, primary / secondary subject from the research-area taxonomy with "Other" pending review, interests with reorder), affiliations (several current ones with one primary, "I no longer work here", past affiliations, relationship types), Experience / Education / Memberships (add, edit, ↑↓ reorder, remove; society catalogue, grade list, member number, "Other" society pending review), email addresses (personal / professional, primary), mobile number, address, and Scholar / Professional links (Find: real ORCID and OpenAlex search, other sites open their own search; "Confirm it's you"; Request verification / Withdraw; Remove). Share opens link, QR, vCard and per-network share, plus the Public profile switch; `/author/<slug>` is the read-only view.
- **Honest differences from the prototype** (it simulates these; this app does not pretend): *Connect* / *Sign in to verify* explain that platform sign-in isn't available and never mark a link **Verified** (only a stored value from a future real verification would show that badge); the *Confirm* dialog doesn't invent profile statistics; a *verification request* is stored as "Verification pending" and the dialog says no review is connected yet; a secondary email or a changed mobile number is saved as **Not verified** (no link or OTP is faked, and an unverified address can't be primary); the sign-in email is shown verified and read-only; the Share dialog says the link **opens for you only** until `supabase/migrations/0027_public_profile.sql` is run: `profile_details` is owner-only, and that migration adds the function `public_profile(slug)` that lets a signed-in person read another person's profile only when they switched Public profile on (name, designation, affiliations, about, timeline, links; never e-mails, phone or address). `/author/<slug>` calls it for anyone else's link and reads “No public profile found” while the function does not exist. Two people with the same name share a slug: the oldest account wins. Admin additions to the grade / relationship / society / research-area lists (Super Admin, on hold) aren't applied, and "Other" entries are stored pending with no review queue behind them. Drag-and-drop reordering of Experience / Education / Memberships rows isn't ported (↑ ↓ buttons are); chips of interests do drag.
- Not ported (documented gaps): the prototype's showcase/"view" mode and share link, experience / education / memberships timelines, past affiliations, multiple emails, link Connect / Find / verification flows (simulated in the prototype), Security & Settings (change password, linked sign-in, merge/delete account), research-area taxonomy and Super Admin master data (institution / department / area lists are the static base list only).

## Security & Settings (`/settings`)

- **Change password**: same two steps as the prototype: the current password is checked first (re-authentication through `signInWithPassword`), then `auth.updateUser({ password })`. "Password updated" appears only after Auth reports success. Rules from the prototype: current password required, new one at least 6 characters, retype must match (plus "must differ from the current one"); the server's own rules (weak password, same password) are shown in plain words. Passwords are only passed to the Auth API (never logged, stored or put in a URL). An ended session sends the user to login. The prototype's "password changed" email note is not shown: nothing here sends one.
- **Notifications**: email frequency (Instant / Daily / Weekly / Off) and, when a mobile number exists, SMS / WhatsApp switches. Stored in `profile_details.data` (`notifyFrequency`, `notifyChannels`), the prototype's own persistence; merged, so other keys survive. "Saved" is shown only after the write succeeds. **Gap:** nothing in this repo reads these values yet (no digest or SMS/WhatsApp sender), so they are stored but have no delivery effect.
- **Display & Accessibility**: timezone (237 options, stored as the label, e.g. "India | GMT +05:30"; empty = browser timezone) and Color-blind mode. The palette (`:root[data-colorblind]` in tokens.css) follows the *saved* value and applies on every signed-in page. **Gap:** nothing displays dates in the saved timezone yet.
- **Not included**: linked sign-in methods, merge accounts, delete account (out of scope), and the Privacy toggles (shareable public profile, reviewer badges): their targets (public profile page, reviewer achievements) aren't ported, so a saved toggle would have no effect here.

## Notifications (`/notifications`) and the header bell

The prototype is the reference (`src/author-module/NotificationsPage.jsx`, `notificationsData.js`, and `liveAlertOf` / `TopNav` in `src/author-journey.jsx`); this page reproduces its global Notifications page.

- **Data:** the signed-in user's own rows of `notifications` (the bell): the latest 100, newest first, with their conference (`conferences(slug, acronym)`). Row Level Security ("notifications: own", "notifications: mark read") and the column grant (only `read_at` is writable) decide what is allowed, and every query also names the user. No schema, trigger or policy was added. The `link` column is deliberately **not read**.
- **Tabs:** All, Paper updates, Announcements and Emails, with the prototype's own test (`tab === "all" || category === tab || (tab === "update" && category === "action") || (tab === "email" && isEmail)`). The kind → category mapping is the prototype's `liveAlertOf` (`src/features/notifications/kinds.ts`). **Emails** shows copies of the emails the platform sent to the signed-in account, read through the `my_emails()` database function (migration `supabase/migrations/0026_my_emails.sql`: only `status = 'sent'` rows whose recipient is the profile's own address; `email_log` itself stays readable by chairs and admins only). Each item shows the subject, "From <conference> <contact address>" and a two-line preview, with "Open paper" (the author's paper, or the reviewer's review page; only when the paper is known, on the prototype's page for now) and "View email". "View email" opens the prototype's viewer: subject, template chip, From / To / Sent and the email as it was sent, in the same branded frame (`lib/email-frame.ts`, a port of `emailFrameCore.js`) inside a sandboxed iframe (no scripts, a Content-Security-Policy with no script, form or connection, links open in a new tab). An email has no read flag in the database: like the prototype, one older than two days starts read, and read / unread, "Mark all as read" and Dismiss for emails are kept by the page for the visit only. The header bell counts stored notifications only, not emails: counting them would need the emails query on every page (open question for the product owner; the prototype's bell counts its in-memory email items). If the function is missing (migration not run) or fails, the notifications still load and a message with "Try again" is shown above the list.
- **Groups and rows:** Today / This week / Earlier, newest first within each group. Each row: unread dot, the kind's icon tile (the prototype's `KIND_META`), title, a conference chip "ACRONYM · Role" (the role is the prototype's audience for that kind; a withdrawal is the chair's copy when the account chairs that conference), body, the action button (below) and, on the right, the time with the read / unread toggle and Dismiss. Clicking the card (not one of its buttons) does its action. Titles and bodies are stored text and are rendered as text.
- **Header bell:** the prototype's bell and badge (a link here), unread number up to "9+", lit on the page. One lightweight count query per load of the signed-in app shell; no polling, no realtime. If the count query fails the bell shows no number until the page's own rows give it one.
- **Read / unread:** the toggle on each card marks it read or unread again (writes only `read_at`, for this user's row). "Mark all as read" marks **every** unread notification of the user, whichever tab or conference is showing and including rows beyond the 100 listed. Nothing is shown as changed until the update succeeded; a failure keeps the row as it was and the header number, and shows an error. Requests do not overlap.
- **Dismiss:** the card leaves the list for this visit and the header number follows. As in the prototype (its list is in memory) a reload brings it back; nothing is deleted, because the database gives users no way to delete a notification.
- **Action buttons:** the prototype gives each database notification one action with its own label (`liveAlertOf`), and so does this page. Three go to pages of this app ("See the invitation" and "Open My Conferences" → `/dashboard`; "Open my submissions" → `/author/<conference>/submissions`, ported with the Author workspace). The others open the prototype's own page on `NEXT_PUBLIC_PROTOTYPE_URL`, as the navigation menu does for screens not ported yet (approved 2026-10-29): "Open my review queue", "Open my review" (that paper, else the queue), "Open submissions", "Open reviewers", "Find a replacement", "Open Initial Check" and "Open my paper". A paper page needs the paper's label (`ISBM-680`): the notification query embeds `submissions(paper_no)` and builds it like the dashboard does; without it (Row Level Security hides the paper) there is no button, as in the prototype. Slugs and paper labels are validated and URL-encoded; the stored `link` is never read. **When one of those pages is ported, change its `prototype` target to `app` in `features/notifications/destinations.ts`** (the table at the top of that file lists every kind, label and page). The conference chip is not a link yet, for the same reason.
- **"How should we tell you?" box:** the prototype's three boxes, kept as page state only, as there. Settings has the real notification preferences.
- **Not included:** attachments on emails (the log keeps none), realtime, pagination beyond 100. Times use the browser's timezone. The Author workspace's "Updates" page (the same inbox for one conference) is not ported.
- **Mock mode** (`NEXT_PUBLIC_DATA_SOURCE=mock`): fixtures in `src/mocks/notifications.ts` (every kind, an unknown one, one announcement, one without a conference), kept in memory; no network.
- **Verification:** checked with mock data and with a fake local Supabase (Row-Level-Security-like filtering, failure and delay switches) only; the same reads and the `read_at` writes have **not** been run against a real Supabase project.

## Author workspace (`/conference/<conference>/author`, `/author/<conference>/submissions`, `/submissions/<paper>/author`)

The Author workspace: Dashboard (Overview), My Submissions and a paper's own page (Reviewer and Chair workspaces follow). `<conference>` is the conference's slug, the id My Conferences uses; `/author/<slug>` alone is still the public person profile.

- **Frame** (`features/workspace/components/author-shell.tsx`, the prototype's Sidebar + ConferenceShell): the conference card (monogram, acronym, name), "Viewing as Author" (a role switcher when the account holds more roles there; other roles open the prototype's workspace), "Switch conference" (the account's other conferences as an author), the menu (Dashboard, My Submissions, My flyer, Certificates, Feedback, Updates, Activity Log), "My Conferences". Menu items for screens that are not ported open the same page in the prototype (`NEXT_PUBLIC_PROTOTYPE_URL`); Dashboard and My Submissions are pages of this app. "Enter" on My Conferences (as author), "Switch conference" and the notification buttons that go to the author's dashboard or submissions open these pages; the other roles' workspaces still open in the prototype. Desktop: the menu can be hidden to a slim rail (kept in this browser's localStorage); below `lg` it folds behind a "Menu" bar and slides in over the page (Esc closes it).
- **Dashboard** (`features/author/components/author-overview-page.tsx`, the prototype's `AuthorHomeD`, the main author page): the conference card (acronym, Active / Archived pill, dates, place, website, "Conference details" drawer, "New Submission"); this conference's numbers (Submitted, Accepted, Rejected, No Decision, and the accepted split Registered / Not Registered / Registration Pending); the to-do list (register, revision / correction required, book a slot, upload and submit, add a photo, feedback) beside the key dates (with "Add to calendar", one date or all, as .ics); once the conference is over, the wrap-up row instead; an archived-early conference shows the chairs' notice. Below, the papers that still need the author, most urgent first (the first 4; "View all" opens My Submissions). The to-do buttons open the prototype's registration, programme, feedback and paper pages for now; "Add photo" goes to this app's `/profile`.
- **My Submissions** (`features/author/`, the prototype's `MySubmissionsPage` / `SubmissionsList.jsx` / `authorStatus.js`): "Your submissions (n)", search (ID, title, author, type), the card sort (Needs me first, Newest / Oldest submitted, Recently updated, Paper ID, Title A–Z, Status), the Cards / Table switch, the clickable count strip (All, Submitted, Accepted, Rejected, No Decision, Registered, Not Registered, Registration Pending, plus Upload Pending and Withdrawn when there are some; clicking the chosen one again shows everything), the status band, ID tag, authors (corresponding author(s) filled, co-authors outlined), dates, track, "Next step" on each card, and the sortable table (ID, Submitted, Last update, Status; withdrawn papers always last). "New Submission" is hidden for an archived conference.
- **Data** (`services/supabase/author-submissions.ts`, as the prototype's `loadWorkspace` / `submissionRow`, author view): the account's own papers in that conference (submitted by them, or listing them as an author), with their authors and uploaded files. What an author is told comes from `notified_outcome` only, so a decision the chair has not sent never shows. "Revision Required" also comes from an open correction / revision request on the newest uploaded version (`submissions.screening`). The conference, its dates, "archived" state and the account's roles come from the same read as My Conferences.
- **A paper's page** (`/submissions/<paper>/author`, `<paper>` is its label such as `ISBM-680`; `features/author/components/author-paper-page.tsx`, the prototype's `SubmissionDetailPage`, author layout): the header (title, status pill, conference, ID, track, dates, withdrawn note) with View submission, Download (latest version), Certificate and Edit, and the author's timeline (Submitted → Under Review → Decision → Registration → Certificate); "Your presentation" once accepted (register first, then slot / flyer / certificate); the correction or plagiarism-revision request on the newest version (what to fix, due date, the similarity score only when the chair shared the report); keywords, abstract, authors (corresponding author, "You"); every file (paper versions newest first, then supporting documents) with view and download; the chair's note and the reviewers' shared comments (never names or scores; only what was sent, so an unsent decision never shows); "Manage submission" with the prototype's lock rules (nothing after withdrawal or a final decision; an accepted paper only for final files). Files are opened through a short-lived link the database signs for the paper's author (`storage.createSignedUrl`, bucket `papers`), as the prototype does for real papers: View opens it in a new tab, Download saves it. **Changing a paper:** Edit / "Update submission" (title, abstract, keywords), "Update / add authors" and "Withdraw submission" are ported (`components/paper-dialogs.tsx`). They save through the database's own functions (`update_paper_details`, `save_paper_authors`, `withdraw_submission`, migrations 0007 / 0022, which decide who may change the paper and refuse once a decision is recorded) and show a failure inside the dialog. After a save the paper is read again. Authors added to a paper get the co-author email, and a withdrawal emails the authors and chairs: this app has no email server, so `app/api/send-email/route.ts` passes the request, with the user's own sign-in token, to the prototype's `/api/send-email` on `NEXT_PUBLIC_PROTOTYPE_URL` (server to server, so no CORS; only `submission_withdrawn` and `paper_authors_updated` can be passed on, and the email server checks the user again). If that server is down or refuses, the change stays and a notice says "Saved, but the emails weren't sent: …". The prototype server therefore has to be running (with `RESEND_API_KEY` etc.) for those emails. **Files:** "Update files" (also "Upload version N", "Upload revised paper" and "Add supporting document") uploads a new version of the paper or a supporting document: only PDF or Word, up to 25 MB (checked here and again by the storage bucket), put in the private `papers` bucket under `<conference id>/<paper id>/` and recorded in `submission_files` (kind `revision` with the next version number, or `supplementary`); the database moves a paper that was waiting for its upload on to review, and a new version asks the email server for `paper_revised`, which rings the chairs' bell ("New version of … to check"). Rows and bucket are protected by Row Level Security: only an author of the paper can add files. Nothing is deleted. **Not ported / different from the prototype:** the automatic PDF check (page count, editable, language, layout; pdf.js and an AI call in the prototype) and the AI preparation of the new file (`requestPaperIngest`), so the chairs' Initial Check opens without the pre-filled automatic result for a version uploaded here; the "What changed?" note and the supporting-document type and removal (the prototype keeps them only in the browser for real papers, the database has no place for them, so a supporting document is stored as "Supplementary material" and cannot be removed here). "Continue editing & submit" (finishing a draft) still opens the prototype's page. Cards, rows, "Open my paper" and an author's email "Open paper" lead to this page.
- **New Submission** (`/submit/<conference>`, `features/author/components/submit-paper-page.tsx`, the prototype’s `SubmitPaperPage` with its default submission form): the paper file (PDF / Word, 25 MB), title (with the duplicate-title warning from `check_duplicate_submission`), abstract, keywords, submission type, track (the conference’s `tracks`, else “General Track”), the authors (the signed-in author is Author 1 and must stay on the paper; reorder, corresponding author, no repeated email), and the two declarations. Sending inserts the paper, its authors and the file (`submissions`, `submission_authors`, `submission_files` + the `papers` bucket) and asks the email server for `submission_received`; then it goes to My Submissions. The page has no conference sidebar so a first-time author, who has no role there yet, can use it. **Submit on behalf** (`/chair/<conference>/submit-behalf`) first asks the chair for the author’s name and email, then shows the same form with that author as Author 1 (`submission_on_behalf`). **Not ported yet:** the automatic fill from the PDF (pdf.js and an AI call), the automatic PDF check saved with the file, the AI preparation of the paper, saving a draft (so “Continue editing & submit” opens a new form), and a chair-edited submission form (the database keeps none).
- **Dashboard gaps, because the database has nothing for them:** the organisers' call for papers (topics, guidelines, speakers, committees, sponsors, the submission deadline). As in the prototype for a conference without one, the key dates are worked out from the conference's start date (full paper due 75 days before, abstract 30 days before that, results 42 days after the full-paper date, final version 14 days before the start), the deadline chip is not shown and the drawer says no full call for papers was published; the drawer's "About" is the conference name and Tracks lists "General Track". The conference logo is not shown (only the monogram). There is no certificates table and nothing stored for feedback, so the wrap-up says "No certificate yet" and always asks for feedback (as the prototype's session-only store does).
- **Paper page gaps:** the plagiarism / similarity report files (the database keeps no report files, so there is no "Download report" and no list of earlier reports); the certificate (no certificates table, so the button is always off); the presentation slot (no programme tables); the organisers' "Allow edits after acceptance" switch (not in the database, so it is treated as off, the prototype's default); a stored supporting document needs a stored file to be viewed or downloaded (one without a stored file shows its row with the buttons off).
- **Gaps, because the database has nothing for them:** the chair's custom "Author sees" wording (the table has no such column, so every status uses the agreed default label, which is what the prototype shows in database mode too); the presentation slot (no programme tables), so a registered paper reads "Book your presentation slot" and never "You're all set"; whether the Call for Papers is closed (`cfpClosed` is not read), so "New Submission" depends on the conference being archived only; co-author photos (initials only, as in the prototype's database rows). The not-yet-built menu pages above are the other gap.

- **Updates** (`/author/<conference>/updates`, `/reviewer/<conference>/updates`, `features/notifications/components/conference-updates-page.tsx`): the Notifications inbox narrowed to what that conference sent to that role (`audienceOf`), inside the conference frame; the global Notifications page is unchanged.

- **AI functions through a proxy** (`app/api/ai/[name]/route.ts`, `services/paper-ai.ts`): like the email proxy, the app passes `ingest-paper`, `paper-chat` and `enhance-review` on to the prototype’s server (`PROTOTYPE_URL`) with the user’s own sign-in token; the server checks the user again, calls the model and records the cost in `ai_usage`. A new paper (New Submission) and a new version (Update files) ask for `ingest-paper` in the background. The paper chat and the reviewer’s AI help have no screen here yet (P2 leftovers); `askPaper` is ready for them.
